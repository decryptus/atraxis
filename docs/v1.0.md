# Atraxis 1.0: supported reference configuration

Atraxis 1.0 provides read-only inventory and authenticated operator interfaces.
The reference configuration below defines its qualification boundary. Optional
engines and executors remain separately installed, explicitly authorized services.
A stable Atraxis package does not turn its alpha Atropos dependencies into stable
upstream releases or qualify every possible backend and destination.

| Component | Reference configuration | Boundary |
| --- | --- | --- |
| Atraxis package | 1.0.0; Python 3.11 or 3.12; Linux amd64 | Installed CLI, API, web and optional Textual interfaces |
| Operator Compose | Python 3.12; verified TLS; SQLite accounts and engine storage; integrated queue | Single-host operation and coordinated cold recovery onto a distinct host; workers opt-in |
| Atropos service/client | `atraxis-atropos` 0.1.0a21 / `atropos-client` 0.1.0a10; source `dedb114217c3df5fe0ab79d7acc53cd5636ebee0` | Independent alpha dependencies; existing version-1 YAML rules/workflows and ZEN 2.1.2 |
| Native sources | Direct `monit_docker` and `certlord` | Automatic resource discovery; full native fields including certificate domains, versions and fingerprints |
| Indirect native sources | `prometheus_monit` and `prometheus_certlord` through Covenant and Prometheus | Same native projection with collection/scrape delay; bounded snapshot size and explicit freshness |
| Selected metrics | Generic `prometheus`; Covenant optional | Explicit numeric selections; does not reconstruct native inventories |
| Execution | Explicit source-bound rule and immutable binding; Auton 1.3.1 source `7f57348b144fa62400bad31160d4b4ad5c00f53c` with the documented bounded transport patch | One non-destructive HTTPS diagnostic reference; arbitrary scripts, container remediation and unattended policies require their own approval and qualification |
| Notification | Existing Alertmanager adapter and a local webhook receiver | Actual firing and resolution verified locally; external email/SMS/chat and human receipt are outside this reference |
| Optional storage | Existing JSON account and Redis/PostgreSQL/MySQL/MariaDB engine adapters | Retained implementation and contract tests; no additional operational recovery or capacity promise |

Use the [setup guide](setup.md), [operator journey](operator-journey.md) and
[Compose guide](docker-compose.md). Locked Compose inputs are recorded in the
repository's `deploy/compose/locks/`; follow the documented matching source pins.
The operational qualification also covered the preceding web dependency set
(PyCurl 7.48.0 and PyCryptodome 4.1.0); this does not extend to arbitrary upgrades.

## Select adapters without adding unnecessary services

Prefer direct `monit_docker` and `certlord` when their APIs are reachable. Neither
requires Covenant or Prometheus, and individual containers/domains need no manual
list. The optional indirect routes require Covenant's `monit_observation` and
`certlord_observation` plugins from source
[`331e56367ef92ff24a5f3931b650d9301a298bed`](https://github.com/decryptus/covenant/commit/331e56367ef92ff24a5f3931b650d9301a298bed).
Published Covenant 0.0.72 does not contain those plugins. Legacy metric plugins
cannot supply the complete native inventories. See [adapter selection](source-configuration.md#choose-an-adapter),
the [Monit guide](prometheus-monit.md) and [CertLord guide](prometheus-certlord.md).

Unknown, unavailable, authoritative empty and historical data remain distinct.
No automatic direct-source fallback or cross-source deduplication is introduced.
The 10,000-row and 4 MiB transport limits reject oversized snapshots as a whole.
Changing labels and Prometheus retention have storage costs; qualify your actual
inventory and history window before selecting capacity.

## Operation and recovery

Saving/testing does not activate a rule; activation does not dispatch an action.
Execution requires current permissions, an exact generation, an approved binding
and signed current observations. Test contexts remain isolated and use registered
simulators only; missing simulation support never falls back to a real effect.
An uncertain action must be inspected and reconciled before an explicit retry or
resume. Submitting a notification is not evidence of downstream receipt.

Cold recovery preserves accounts, audits, configurations and persistent state,
checks current authority, verifies renewed TLS certificates, and leaves execution
paused. Do not apply a stale backup over newer revocations or resume uncertain
external effects automatically. A coordinated application backup is not a complete
host backup, an off-site retention policy, high availability or hot backup.

This release retains the measured four-hour synthetic SQLite/Redis workload at
its original inputs. It does not claim that workload ran on the operational
integrated queue, guarantee production throughput, indefinite history retention,
or establish absence of memory leaks. The reference supports the documented
bounded behavior, not a service-level objective.

## Upgrade and format boundary

The runtime Python modules are unchanged from the operationally qualified
`1.0.0rc1` build; 1.0 finalizes package identity, documentation and publication
checks. Back up the application state before replacing an installation and use
matching client/service versions. Current API/configuration/storage formats are
explicitly versioned; unsupported formats fail without automatic conversion or
deletion. Prototype compatibility and arbitrary component combinations are not
promised. SSO, new backends, graphs, automatic metric-to-intervention wiring,
high availability and hot backup remain later work.
