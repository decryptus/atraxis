# Atraxis 1.0.4

## Upgrade behind a proxy

Before upgrading a web listener bound to a non-loopback address, identify the
IPv4 address from which its TLS proxy connects. Set both keys in the service
configuration. Replace the documentation address below with the actual peer.

```yaml
general:
  behind_tls_proxy: true
  trusted_proxy_networks:
    - 192.0.2.10/32
```

Run `atraxis check-config --config /etc/atraxis/atraxis.yml` with the candidate
binary before switching the service. A loopback listener needs no new setting.
After restarting, check an authenticated request through the proxy. The backend
drops connections from peers outside the configured ranges.

## Operator changes

Repeated failed Basic authentication attempts receive HTTP 429 with a
`Retry-After` header. The 60-second limits apply to a TCP peer and account
together (eight failures), and to the peer across accounts (64 failures).
Clients behind one proxy share its allowance. Rule forms now validate their
tokens separately for each action. Inventory navigation preserves scoped
links and displays the source's original values.

The package supports Python 3.11 through 3.13. The guided Compose installer
uses the previously published 1.0.3 web image pinned by digest. The CLI and
native systemd deployment use the installed package.

## Qualification

The candidate wheel with HTTPdis 0.6.39 read fresh observations from four pilot
sources. A distinct isolated restore recovered ten services and two SQLite
databases. TLS renewal, replacement login, rejection of revoked credentials
and throttling of repeated failed logins passed. Both queues stayed paused
with zero workers. The [synthetic two-hour run](https://github.com/decryptus/atraxis/actions/runs/41990264095)
is pending. The stable publication gates remain open until the results are reviewed.
